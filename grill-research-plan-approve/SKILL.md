# 先调研后规划

把一个任务、项目或想法变成经过用户批准的可执行工作，而不是接到请求就直接写文件。

核心顺序：

```text
复述目标 -> 只读检查 -> 只问关键决策 -> 找类似项目 -> 推荐可用 Skill
-> 给建议 -> 出简短计划 -> 等待明确批准 -> 再实施
```

## 何时使用

用于需要设计、实现、修改多个文件或改变外部状态的非平凡请求：

- 新项目、新产品、新功能、页面、工具、自动化或工作流。
- 重构、迁移、架构选择、技术选型和集成。
- 用户只有粗略想法，验收标准或实现路径尚不明确。
- 可能已有类似项目、开源实现、模板或现成 Skill。
- 用户要求“先问我”“先调研”“先规划再动手”。

以下情况不要触发：

- 用户在问知识、解释、比较或建议，并没有要求实施。
- 明确、局部、可逆的一步修改。
- 用户明确说“直接做”“不用问”“立即执行”，且没有高风险歧义。
- 正在处理紧急故障：先做安全的只读诊断和止损，不要为了流程拖延。

## 原则

- **事实自己查，决策问用户。** 能从文件、Git、文档、搜索或工具确认的，不要问用户。
- **不要一次问一整张问卷。** 普通任务只问 1～3 个会改变方案的问题。
- **每个问题都给推荐答案和理由。** 用户不回答时，可以按“推荐”继续。
- **用户批准前只读。** 不创建、修改或删除目标文件，不安装依赖，不提交、推送、部署或调用有副作用的外部接口。
- **计划要短。** 默认 3～7 个实施步骤，足够另一个工程师执行即可，不写完整代码。
- **不要把自己选择的方案当成用户已经同意。**
- **不确定就明确说不确定。** 不伪造类似项目、安装量、Star 数或 Skill 能力。

## 工作流

### 1. 复述目标

用 1～2 句话说明你理解的目标、用户和完成标准。若理解有歧义，先只问一个最关键的澄清问题。

### 2. 快速只读检查

在不修改任何东西的前提下，检查当前任务真正需要的上下文：

- 当前工作目录、已有文件、`AGENTS.md` 和项目说明。
- Git 状态、技术栈、入口、依赖、测试和构建命令。
- 现有实现、约定和可能受影响的范围。

不要为了“看得更全”而扫描无关目录。能在仓库里查到的，不要问用户。

### 3. 只问高影响决策

优先确认会改变方案的事项：

- 最终目标与验收标准。
- 这次必须做什么、明确不做什么。
- 平台、技术栈、兼容性、时间、预算、权限和数据限制。
- 是否接受参考、复用、分叉现有项目，还是必须从零实现。
- 最不能接受的失败、隐私、安全、成本和可逆性要求。

普通任务每轮只问 1～3 个问题，并给推荐项。每个问题写成：

```text
问题：<一个会改变方案的问题>
推荐：<推荐选择>
理由：<一句理由，以及它会影响什么>
```

如果需求非常模糊或风险很高，读取并遵循 `grilling` Skill，用设计树分轮追问；否则不要为了“盘问”而拖长流程。

用户说“别问了”“按推荐来”“信息够了”时，立即停止提问，列出仍需承认的假设，进入调研和规划。

### 4. 寻找类似项目

对于新项目、非平凡功能或技术选型，先做一次快速同类扫描。用户明确要求时必须做；小修可以直接跳过。

优先查：

- 官方文档、官方示例和官方仓库。
- GitHub、包仓库、模板市场和成熟开源项目。
- 维护活跃、许可证清晰、依赖可控的实现。

比较 2～4 个候选即可，说明：

- 它解决什么问题，是否真的匹配当前需求。
- 最近提交、Release、Issue 活跃度和维护状态。
- License、依赖、安全性、部署成本和与当前项目的兼容性。
- **直接采用 / 分叉改造 / 只借鉴设计 / 从零实现** 哪种更合适。

不要只看 Star 数。不要为了交差硬推项目。找不到合适方案时，明确说“没有找到”，并给出从零实现的理由。

用户批准前，不复制候选代码，不安装依赖，不把候选项目合入目标目录。

### 5. 寻找并推荐 Skill

先检查当前已安装的 Skill，优先推荐真正匹配的现有能力。不要把无关或重复的 Skill 塞进方案。

如果现有 Skill 不够，按 `find-skills` 的方式补充搜索：

- 先看 https://skills.sh/ 的排行榜和常见来源。
- 需要时运行 `npx skills find <query>`。
- 核对安装量、来源信誉、GitHub Star、维护状态和许可证。
- 不要只凭搜索结果推荐；低于 100 安装量或来源不明的 Skill 要谨慎。

推荐时给出：

```text
Skill 名称：
用途：
来源 / 安装量：
为什么适合：
需要安装的命令（如需要）：
```

安装任何外部 Skill 前必须得到用户批准。没有合适 Skill 时，直接说没有，并说明用现有能力怎么做。

避免同时推荐功能冲突的 Skill；例如不要同时推荐两套 TDD、两套调试流程或两个互相争夺“先规划”入口的 Skill。

### 6. 给出建议

对用户不确定的地方，不要只反问。给出：

- 推荐做法。
- 一个合理替代方案。
- 关键取舍和风险。
- 为什么当前推荐更合适。

### 7. 输出简短计划

把计划直接写在对话里，除非用户明确要求生成文件。通常包含：

1. **目标与完成定义**：做成什么，怎样算完成。
2. **范围与非目标**：这次做什么，明确不做什么。
3. **方案与参考**：采用的类似项目、库、模板或 Skill，以及理由。
4. **实施步骤**：3～7 步，按依赖顺序排列。
5. **验证方式**：测试、构建、浏览器检查或人工验收。
6. **风险与回退**：主要风险和可控的回退方式。

计划结束时必须单独写：

```text
等待批准：回复“批准”“开工”或“按这个方案做”。
收到明确批准前，我不会创建或修改文件，也不会开始实施。
```

### 8. 等待明确批准

只有以下表达才算批准：

- “批准”
- “开工”
- “按这个方案做”
- “可以开始”
- “go ahead”
- “implement”

“收到”“知道了”“谢谢”“先这样”“继续调研”不等于批准。若“继续”明确指向上面的计划，可以视为批准；有歧义时先确认一句。

批准只覆盖已经展示的范围。出现以下情况时暂停并重新确认：

- 需要扩大功能范围或修改用户未同意的区域。
- 发现计划依赖的关键假设不成立。
- 需要新增付费服务、权限、不可逆数据操作或重大架构变更。
- 用户改变目标、验收标准或关键约束。

### 9. 批准后实施

- 严格按已批准的计划执行，不擅自扩大范围。
- 使用项目现有模式和工具，保持改动局部、可审查。
- 完成后运行计划中的验证，报告改了什么、验证结果、剩余风险和需要用户验收的事项。

## 回答风格

- 直接、简洁，尊重用户时间。
- 用户不耐烦时，缩小到最后一个高影响问题；没有必要就按推荐假设直接给计划。
- 不把“盘问”当作表演。问题的价值是减少返工，不是制造仪式感。
