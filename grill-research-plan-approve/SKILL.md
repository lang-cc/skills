# 建议、计划、验收后开工

把请求整理成一份能快速判断的方案，不用一串前置问题拖住任务。

## 适用范围

用于会创建或修改文件、改变外部状态，或需要设计取舍的非平凡请求。纯问答、简单一步修改、用户明确说“直接做”的请求，直接处理。

## 核心规则

- **不问关键问题。** 缺失信息采用保守、可逆、常见的默认值，并写明假设。
- **先给建议。** 说明推荐做法、主要理由，以及必要时的替代方案和取舍。
- **说明最终效果。** 用户会看到什么、操作什么、最终得到什么。
- **说明怎么完成。** 给出 3～6 个主要实施步骤，不写完整代码。
- **说明怎么验收。** 用可观察的行为、测试、截图或交付物定义完成标准。
- **调研按需。** 只有用户明确要求，或类似项目、外部 Skill 明显能减少重复工作时才快速查找。
- **批准前只读。** 不创建、修改或删除目标文件，不安装依赖或 Skill，不提交、推送、部署或执行有副作用的操作。
- **批准后不扩范围。** 如果会改变目标、范围或验收标准，暂停并重新给方案。

## 推荐输出

默认用以下格式，简单任务可以进一步压缩：

```text
建议方案：

预计效果：
- 用户看到：
- 用户可以操作：
- 最终交付：

默认假设：

完成步骤：
1.
2.
3.

验收标准：
- [ ]
- [ ]
- [ ]

参考项目 / Skill：无；或列出 1～3 个并说明理由
主要风险与回退：
```

## 工作流

1. **理解请求并补全假设**

   用 1～2 句话复述目标。信息不足时直接选推荐默认值；只有错误假设会造成不可逆损失时，才突出风险。

2. **做必要的只读检查**

   查看当前目录、已有文件、`AGENTS.md`、Git 状态、技术栈、入口、依赖、测试和受影响范围。能从文件或命令确认的事实，不要问用户。

3. **给建议并说明效果**

   直接推荐一个方案，说明为什么适合、预计做成什么样、有什么限制或回退方式。需要时再快速找 1～3 个类似项目或已安装 Skill；不要为了流程强制搜索。

4. **输出简短计划**

   写清默认假设、3～6 个实施步骤和可执行的验收标准。需求简单就压缩成：

   ```text
   建议：……
   完成：……
   验收：……
   等待批准。
   ```

5. **等待明确批准**

   方案末尾必须写：

   ```text
   等待批准：回复“批准”“开工”或“按这个方案做”。
   收到明确批准前，我不会创建或修改文件，也不会开始实施。
   ```

   “收到”“知道了”“谢谢”“先这样”不等于批准。若“继续”明确指向上面的方案，可以视为批准；有歧义时先确认一句。

6. **批准后实施**

   严格按已批准的范围执行，使用项目现有模式和工具。完成后按验收标准实际检查，报告改了什么、怎么验收，以及仍需用户确认的事项。

## 风格

直接、简洁，先给推荐，再给假设、步骤和验收。不要用盘问代替判断，也不要把方案写成冗长文档。
